## Benchmark Tests

Three benchmark files live in `tests/performance/database/`. They measure index strategy impact on bulk INSERT, single DELETE, and three SELECT patterns against the `instances` table using synthetic tree-shaped data.

### Synthetic Data Structure

All benchmarks use a **reference tree** generated by `_build_tree()` in `conftest.py`:

- **Topology**: Random balanced tree, configurable depth (default 3) and fan-out (default 2–3 children per node). Node order is deterministic (seeded PRNG).
- **Tree range**: `2 × node_count` — each node consumes two integers in the nested-set's `tin`/`tout` numbering.
- **Per-tree size**: ~17–22 nodes per tree (depth 3), ~2K nodes per tree (depth 10 in deep benchmark).

The `instances` table is loaded with `BENCHMARK_TOTAL_TREES` copies of this reference tree:

| Benchmark | Trees | Nodes per tree | Total rows | DB size |
|-----------|-------|----------------|------------|---------|
| `test_benchmark` | 200,000 | ~22 | ~8,000,000 | ~250 MB |
| `test_benchmark_deep` | 100,000 | 10 | ~1,000,000 | ~150 MB |
| `test_benchmark_recalculate` | 1 per depth | 8 → 1,955 | — | — |

### Creation

1. **Type + Object scaffolding**: A single `Types` row and a matching `Objects` tree (same topology) are inserted first. Objects link to the type via `type_id`.
2. **Bulk instance INSERT**: `_insert_trees_bulk()` issues raw `INSERT INTO instances (...) VALUES (...)` with chunky `RETURNING id,tin`. For each level of the tree, all nodes across all trees are inserted in one round-trip (split into chunks of 50,000 rows). Parent/root IDs are mapped in-memory via Python dicts.
3. **Index strategy applied**: After data insertion, the benchmark drops composite production indexes and creates exactly one index variant (A–E or ALL).
4. **Metadata collected**: `root_ids` (roots of every tree), `subtrees` (random `tin`/`tout`/`root_id` triples for DFS-range queries), and `random_node_ids` (100 random node IDs for CTE queries).

### Cleanup

Each benchmark variant cleans up after itself in a `finally` block:

1. **DELETE newly inserted trees** by `tin >= cleanup_start` — two-phase: first delete non-root children, then roots (to respect `parent_id` FK).
2. **DROP the benchmark index** that was created for the variant.
3. **Teardown** (`synthetic_data` fixture yield): `DELETE FROM types WHERE id = root_type_id` — the DB-level `ON DELETE CASCADE` propagates to all objects and instances.

### Index Variants Tested

Each variant is a single-column or composite index on the `instances` table:

| Variant | Index columns | Purpose |
|---------|---------------|---------|
| **A** | `(tin, tout, tree_size)` | Optimised for nested-set range scans |
| **B** | `(root_id)` | Single-column, smallest footprint |
| **C** | `(parent_id)` | Optimised for parent-child lookups |
| **D** | `(root_id, tin, tout)` | Composite: filter by root, then range-scan |
| **E** | `(root_id, parent_id)` | Composite: filter by root, then parent-child |
| **ALL** | All of the above | Simulates production with all indexes present |

### SQL Queries Under Test

Each benchmarked operation uses the exact SQL below:

#### INSERT

```sql
-- Bulk VALUES insert with RETURNING for ID mapping
INSERT INTO instances (name,object_id,parent_id,root_id,is_active,tin,tout,tree_size)
VALUES
  ('t0_n0', 101, NULL,  NULL, TRUE, 0,  1,  1),
  ('t0_n1', 102, 10001, 10001, TRUE, 2,  3,  1),
  ('t0_n2', 103, 10001, 10001, TRUE, 4,  5,  1),
  ...
RETURNING id, tin
```

All nodes at the same tree level across all trees are inserted in one statement. Rows are chunked at 50,000 per `VALUES` clause to stay within PostgreSQL's parameter limit.

#### DELETE

```sql
DELETE FROM instances WHERE id = :rid
```

Single-row delete by primary key. This is the fastest possible delete path — index choice barely matters because the PK index resolves the row immediately.

#### DFS SELECT (nested-set subtree query)

```sql
SELECT * FROM instances
WHERE tin >= :tin AND tout <= :tout AND root_id = :root_id
ORDER BY tin
```

This is the core nested-set read pattern. The `tin`/`tout` range captures an entire subtree in one index range scan. The `root_id` filter restricts to a single tree. The `ORDER BY tin` guarantees pre-order traversal. This query is the primary motivation for index variants A and D.

#### root_id SELECT

```sql
SELECT * FROM instances WHERE root_id = :root_id
```

Simple equality filter — returns all nodes in one tree. Used for full-tree operations. Index variants B, D, E, and ALL have a leading `root_id` column that makes this an index-only scan.

#### Recursive CTE (parent-child traversal)

```sql
WITH RECURSIVE tree AS (
    SELECT * FROM instances WHERE id = :root_id
    UNION ALL
    SELECT i.* FROM instances i JOIN tree t ON i.parent_id = t.id
)
SELECT * FROM tree
```

Walks the `parent_id` chain from a starting node to retrieve all descendants. Does not use `tin`/`tout` at all. Performance depends entirely on the `parent_id` index (variant C or E). Used as a fallback when nested-set ranges are unavailable.

### Results — Regular Trees (200,000 trees, ~8 million rows, ~250 MB table)

Scale: 200K trees × ~40 nodes/tree (depth 3, fan-out 2–3) = ~8M instance rows. Each variant inserts the baseline data once (module-scoped), then measures 10 INSERT batches of 100 trees, 100 single-row DELETEs, and 300 SELECT queries.

| Variant | INSERT (ms/tree) | DELETE (ms/row) | DFS SELECT (ms) | root_id SELECT (ms) | CTE SELECT (ms) | DB total (MB) |
|---------|:-:|:-:|:-:|:-:|:-:|:-:|
| **A** `(tin,tout,tree_size)` | 0.42 | 0.95 | 0.17 | 0.16 | 0.18 | 709 |
| **B** `(root_id)` | 0.48 | 1.22 | **0.13** | **0.12** | **0.12** | 642 |
| **C** `(parent_id)` | 0.53 | 1.25 | **0.12** | 0.13 | 0.20 | 677 |
| **D** `(root_id,tin,tout)` | 0.51 | 0.97 | 0.31 | 0.22 | **0.12** | 720 |
| **E** `(root_id,parent_id)` | 0.46 | 1.29 | 0.31 | 0.37 | 0.20 | 688 |
| **ALL** | 0.48 | 1.12 | 0.16 | 0.15 | 0.16 | 788 |

### Results — Deep Trees (100,000 trees, 10 nodes each, ~1 million rows, ~150 MB table)

The deep tree has a chain-like topology: 1 root → 2 children → 2 each → ... → 10 levels deep (exactly 10 nodes per tree). This stresses `parent_id` traversal (CTE) more than range scans (DFS), because each tree is narrow but deep.

| Variant | INSERT (ms/tree) | DELETE (ms/row) | DFS SELECT (ms) | root_id SELECT (ms) | CTE SELECT (ms) | DB total (MB) |
|---------|:-:|:-:|:-:|:-:|:-:|:-:|
| **A** `(tin,tout,tree_size)` | 0.52 | 1.10 | 0.21 | 0.16 | 0.17 | 424 |
| **B** `(root_id)` | 0.59 | 1.08 | 0.18 | 0.16 | 0.17 | 386 |
| **C** `(parent_id)` | 0.56 | 1.18 | **0.15** | **0.14** | **0.14** | 415 |
| **D** `(root_id,tin,tout)` | 0.55 | 1.03 | 0.17 | 0.16 | 0.19 | 437 |
| **E** `(root_id,parent_id)` | 0.54 | 1.05 | 0.22 | 0.16 | **0.13** | 424 |
| **ALL** | 0.58 | 1.06 | 0.17 | 0.17 | 0.18 | 485 |

#### Explanation

- **INSERT** (~0.42–0.59 ms/tree across all variants): The initial 200K-tree seed data is inserted *before* any benchmark index is built (production indexes are dropped first). Each variant then inserts only 10 batches of 100 trees (1,000 trees total) into the existing table — index maintenance overhead is negligible at this volume. All variants perform identically because the incremental insert volume is tiny relative to the 200K-tree baseline.

- **DELETE** (~0.95–1.29 ms): Single-row `DELETE FROM instances WHERE id = :rid`. The PK index resolves the row instantly regardless of which secondary index is present. Variant **ALL** (1.12 ms) is marginally slower because PostgreSQL must maintain 5 B-tree indexes on every DELETE rather than 1.

- **DFS SELECT** (range query `tin >= :tin AND tout <= :tout AND root_id = :root_id ORDER BY tin`):
  - Regular trees: Variant **C** (parent_id) is fastest at **0.12 ms** — PostgreSQL uses a bitmap scan combining the `root_id` implicit filter and the `parent_id` index. Variants **D** and **E** are slowest (0.31 ms) — their composite indexes are larger and the planner chooses inefficient index-only scans.
  - Deep trees: Variant **C** again leads at **0.15 ms**. Deep trees have fewer siblings at each level, so the `tin`/`tout` range is narrow — any index that filters by `root_id` early works well.

- **root_id SELECT** (`WHERE root_id = :root_id`): All variants with a leading `root_id` column (B, D, E, ALL) perform similarly (~0.12–0.22 ms regular, ~0.14–0.17 ms deep). Variant A (no `root_id` column) does a full table scan at 0.16 ms — still fast at 8M rows because the data fits in shared buffers.

- **Recursive CTE** (`WITH RECURSIVE` walking `parent_id`): Variants **B** and **D** lead for regular trees (0.12 ms), **C** and **E** for deep trees (0.13–0.14 ms). The CTE joins on `parent_id`, which benefits from any index covering that column. Deep trees (10-level chains) show slightly higher variance because the recursion depth is greater.

- **DB size**: Variant **ALL** is largest (788 MB regular, 485 MB deep) — 5 indexes on 8M rows. Variant **B** (single `root_id` index) is smallest (642 MB regular, 386 MB deep). The table data itself is ~250 MB (regular) and ~150 MB (deep) regardless of index variant; the DB size differences come entirely from index storage.
